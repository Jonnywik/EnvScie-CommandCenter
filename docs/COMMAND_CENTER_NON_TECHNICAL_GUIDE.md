# Code for Resilience Command Center

## A plain-language guide for emergency responders and LGU staff

**Audience:** Balangiga LGU staff, DRRM personnel, dispatchers, evacuation-center managers, public-information staff, and partner response groups.

> **Purpose:** The Command Center helps people make, record, and coordinate safer emergency-response decisions. It brings together emergency requests, verified warnings, evacuation capacity, field teams, supplies, maps, and communication updates in one working screen.

This guide explains how to use the system without needing any programming knowledge. The Command Center does not replace the incident commander, responders, or official government warnings. It helps them see the same operational picture and keep a clear record of what was checked, decided, and assigned.

## 1. What the Command Center is for

During typhoons, floods, storm surges, and other emergencies, information can arrive quickly from many places: residents, radio traffic, SMS messages, social media, weather agencies, barangay officials, and field responders. The Command Center organizes that information so the team can identify urgent needs, verify what is known, send the right group, and track whether the work was completed.

The system is designed around a simple principle: **check first, decide clearly, assign responsibly, and record the result.** It supports both a live connection and a saved, or *cached*, picture of the last information received.

| The system helps you | The system does not do by itself |
|---|---|
| See emergency requests, warnings, teams, centers, supplies, and communications together. | Replace human judgement or authorize evacuation orders automatically. |
| Highlight stale information that should be checked again. | Guarantee that a person, vehicle, or center is available without field confirmation. |
| Suggest a response group based on severity, specialty, location, readiness, and constraints. | Dispatch a team without an authorized user reviewing the recommendation. |
| Keep a record of reviews, assignments, and updates. | Replace official PAGASA, LGU, police, fire, health, or disaster-management procedures. |

## 2. Starting the system

When the Command Center opens, you first see a short loading screen with the Code for Resilience emblem. This screen means the system is collecting the latest available emergency picture. It checks the status of alerts, SOS requests, evacuation centers, map layers, response groups, communications, and delivery records.

After loading, the main dashboard appears. If the system is connected to the latest sources, you will see **Live operations**. If a connection is temporarily unavailable, you may see **Cached snapshot**. A cached snapshot is still useful, but it may be old. Before making a dispatch or public-safety decision from cached information, contact the relevant field team or source and confirm the details.

### Working faster without skipping safeguards

The Command Center remembers the last command area you used on that browser. This makes it easier to return to the same workspace after a short interruption. It does not replace the need to review the **Command Readiness Board** at the beginning of a shift or before an important decision.

Select **Quick keys** to see available shortcuts. You may use the number keys **1–9** to switch between command areas, **R** to refresh the operational picture, **N** to open the manual emergency form for a coordinator-reported incident, **?** to open the Quick keys panel, and **Escape** to close an open drawer or panel. The shortcuts do not dispatch a team, close an SOS, send a bulletin, or approve a warning. They also do not work while you are typing into a form, so they will not interfere with writing an emergency report.

The **Quick keys** panel also contains a **Copy handoff** button. It prepares a short briefing for the next duty officer with open SOS reports, priority alerts, notification-delivery issues, and a reminder to re-check information before acting. Share this only through the LGU’s approved communication channel. The incoming officer must still confirm field conditions, acknowledgements, and route safety.

## 3. The first screen: Situation Overview

The **Overview** screen is the starting place for every shift. It gives the duty officer a quick view of what needs attention now. Begin here at the start of a shift, after a major update, and before issuing a new deployment or public movement order.

The four large number cards show the most urgent high-level information: untriaged SOS requests, critical alerts, open evacuation centers, and residents at risk. A sudden increase in any of these numbers should prompt a closer review in the related screen.

### The Command Readiness Board

The **Command Readiness Board** highlights five safeguards. It is not an automatic clearance system. Instead, it reminds the command team what must be checked before taking a high-impact action.

| Readiness item | What it means | What to do |
|---|---|---|
| Unacknowledged SOS | Someone has requested help but has not yet been triaged or acknowledged. | Open **Live SOS**, review the request, and record the next action. |
| Stale response groups | A team’s location or roster check-in is older than the required freshness window. | Contact the team or ask for a check-in before using its location to dispatch. |
| Stale official feeds | A warning source has not been refreshed recently. | Synchronize or verify the source before issuing fresh public guidance. |
| Constrained centers | A center may be near capacity or missing a required service. | Open **Evacuation Centers**, confirm capacity and services, then update the record. |
| Undelivered assignments | A team may not have received an assignment notification. | Use an alternate channel, such as VHF radio or SMS, and record the acknowledgement. |

## 4. How to handle an emergency request

Use the **Live SOS** screen whenever a resident requests help through the internet, SMS, or a mesh/offline method. Each request shows its reported problem, barangay, time, channel, location confidence, and current status.

An effective response follows this sequence. First, open the request and confirm the location, number of people, immediate danger, and a return contact if available. Next, decide whether the request is life-threatening, urgent, or can safely wait. Then select the appropriate response group or coordinate with the relevant service. Finally, record the action so the next duty officer knows what has happened.

### Recording a report received by the coordinator

Not every emergency starts with a digital SOS. A coordinator may receive a report by telephone, VHF radio, walk-in, barangay relay, or from a field responder. On **Live SOS**, a dispatcher or administrator can select **Record emergency** to place that report in the same triage queue as an SOS request.

Enter the emergency type, urgency, barangay, best available map coordinates, and a short summary of who needs help and what has happened. Reporter name and contact details are optional, but should be included whenever they are safe and useful for a callback. Select **Record and open for triage**. The system labels the new record as **Manual**, keeps a time-stamped audit record of the coordinator’s entry, refreshes the queue, and opens the incident for review.

> **Manual report safeguard:** A coordinator-entered emergency is a serious report, but it is not automatically a verified field situation. Confirm the location, contact details, road conditions, and response-group availability before dispatching a team. If life is immediately at risk, follow LGU emergency procedures without delaying lifesaving action for data entry.

> **Important:** A received SOS is not the same as a verified situation. Treat it seriously, but confirm critical details when time and safety allow. If people are in immediate danger, do not delay lifesaving action merely to complete paperwork.

### Responder-safety assessment for a verified SOS

For an SOS that is verified or acknowledged, open its triage panel and select **Assess responder safety**. The Command Center compares the incident with current operational records for active hazards, nearby response groups, readiness, last location and check-in time, communications, equipment controls, and route uncertainty. It gives each suitable response group a clear risk band and score, then shows the reasons for that score.

The score is **not** a dispatch order, route clearance, permission to enter a hazard area, or guarantee that a responder is safe. It is a structured briefing aid. A high score, stale position, stale check-in, limited communications, missing protective equipment, or route uncertainty requires the coordinator to pause and obtain current confirmation before deployment.

Before a team departs, the Command Center must record the team lead, call sign, personnel count, equipment, departure time, next check-in time, communication channel, and the current route or scene-access confirmation. The field team must confirm its capability, maintain the agreed communication channel, report changing water, blocked access, injury, or loss of contact immediately, and stop or withdraw if actual conditions differ materially from the briefing. The incident commander retains responsibility for the dispatch decision.

> **Responder-safety safeguard:** Never use this assessment alone to justify entry into floodwater, storm surge, unstable structures, landslide areas, or an unverified route. Recheck field conditions, official warnings, communications, route access, and team capability immediately before movement and throughout the task.

## 5. How to use verified alerts

The **Verified Alerts** screen is the place to manage public warnings and source confidence. It distinguishes official or LGU-published updates from information that still needs checking. Use it before preparing an announcement, opening an evacuation center, changing a route, or telling residents to move.

Review the issuing source, the time issued, the expiry time, and the affected area. You can record that an alert was checked or queue a public bulletin. These actions create a visible confirmation so other operators know the item was reviewed. They do not replace the legal approval process for public warnings.

### Provincial weather situation

Use the **Provincial Weather** screen to read the latest available [PAGASA Visayas regional forecast](https://www.pagasa.dost.gov.ph/regional-forecast/visprsd) beside Project NOAH reference datasets for Eastern Samar. This workspace is designed for a provincial briefing before a shift, a weather update, a pre-emptive planning discussion, or a decision to seek more detailed field information.

The top panel reports the published PAGASA regional weather narrative, its stated issue time where available, whether the current source text names Eastern Samar, and whether the dashboard result is current or cached. The warning panel keeps the source wording visible. A statement marked **Regional—verify** may be operationally important, but it is not proof that the warning applies to a specific Eastern Samar barangay. Open the original PAGASA source and confirm its location coverage and validity before using it in public advice or deployment planning.

The Project NOAH cards link to Eastern Samar references for flood risk, landslide susceptibility, and storm-surge advisory scenarios. These are **static hazard models**. They help identify areas that may deserve closer attention, preparedness checks, or field contact. They do not show today’s flood extent, rainfall depth, flooded road, landslide, storm surge, damage, or safe evacuation route. Use the **Open interactive Risk Map** button to compare the latest local operational layers, SOS reports, centers, and route constraints after checking source and field information.

### High-flood-risk assessment

Select **Evaluate flood risk** when a coordinator needs a documented prompt to decide whether additional verification is needed. This is an operator-triggered check; it does not run in the background and it does not contact the public. The Command Center first checks whether a recent PAGASA source is available. It then looks for an applicable official rainfall signal and presents the Project NOAH Eastern Samar flood reference only as static exposure context.

The result may say **Review required**, **Monitor**, **High review required**, or **Source refresh required**. A high or review-required result means the coordinator should immediately check the original PAGASA source, affected barangays, river and coastal conditions, road access, evacuation centers, and field reports. It does not authorize a dispatch, evacuation, public bulletin, SMS, or other public communication. The assessment creates an audit record for the Command Center; the duty officer must review and approve any later operational or public action through the LGU’s normal incident-command process.

> **Flood-risk assessment safeguard:** Project NOAH information never raises the current alert level by itself. It is a static model of possible exposure. If PAGASA source information is stale or unavailable, the assessment does not infer a flood warning; it tells the coordinator to refresh or verify the source first.

> **Provincial weather safeguard:** Before recommending travel, evacuation, public movement, or a field deployment, confirm the relevant PAGASA advisory, time, and geographic coverage; obtain barangay, coastal, river, road, and evacuation-center reports; and follow LGU incident-command procedures. Do not treat a weather narrative or Project NOAH static reference as a safety clearance.

## 6. How to use the risk map

The **Risk Map** combines hazard areas, SOS locations, evacuation centers, tracked resources, and suggested safer movement routes. It is used to answer practical questions such as: “Which road should the rescue truck avoid?” or “Which center is closest without passing through an active flood area?”

The map buttons let you focus on hazards, resources, SOS reports, centers, or routes. Use the route view as decision support. Before sending a team, confirm road and weather conditions by radio, field personnel, or authorized sources. Hazards can move or grow faster than the map refreshes.

### Moving, zooming, and reading the weather layers

The Risk Map itself can be moved without moving the rest of the Command Center page. Drag inside the map to pan, use the mouse wheel to zoom at the location under the pointer, or use the **+**, **−**, and **Reset** controls in the upper-right corner of the map. On a touch screen, use two fingers to pinch and zoom. The map buttons and markers remain usable; the movement controls only affect the visible map area.

Select **Radar** to show the most recent available rain-radar frame supplied through [RainViewer](https://www.rainviewer.com/). Select **Typhoon** to show the current position and listed forecast track points from the public [PAGASA tropical-cyclone bulletin](https://www.pagasa.dost.gov.ph/tropical-cyclone/severe-weather-bulletin) when PAGASA reports an active tropical cyclone. The map badge reports whether a feed is updated, cached, or unavailable. A cached label means the last successful result is displayed after a refresh attempt could not reach the source. An unavailable label means no usable display layer was received.

> **Weather-layer safeguard:** Radar imagery and a tropical-cyclone marker provide geographic context, not proof of rainfall at a specific barangay, road passability, flood depth, storm-surge impact, damage, or safe travel. Check the original PAGASA bulletin, official warnings, field reports, and radio contact before issuing public movement advice or dispatching a team. If life is immediately at risk, follow LGU emergency procedures without waiting for a map layer to refresh.

### Satellite and regional context

Select **Satellite** when you need visual geographic context, such as coastlines, rivers, settlement patterns, terrain, and access corridors. Select **Operational** when you need the simplified map background for a clearer view of hazards, teams, centers, SOS reports, and suggested routes. In either view, the operational layers remain the information that guides coordination.

Select **Regional context** to widen the map from the Balangiga operational area to show the surrounding Eastern Samar setting, including Samar, Leyte, Southern Leyte, and Leyte Gulf. This is useful for understanding an approaching weather system, coastal exposure, possible support routes, or where a provincial coordination request may originate. The wider labels are geographic context only; the current live incident and asset layers remain focused on Balangiga unless the LGU or provincial EOC has loaded verified regional data.

The satellite imagery is supplied by Esri World Imagery and includes its provider acknowledgement. It is **not** a live flood, damage, road-condition, or safety feed. Do not use the appearance of a road, shoreline, bridge, building, or water area in the image as proof that it is currently safe or passable. Confirm changing conditions through field personnel, VHF, authorized warnings, road authorities, or other approved sources before dispatch.

## 7. How to manage evacuation centers

The **Evacuation Centers** screen shows which centers are open, how many people they can receive, how many are already present, and whether important services are available. Examples include water, first aid, power charging, and medical support.

Before directing residents to a center, check its remaining space and service status. If the center is constrained, call the center manager to confirm the situation. Record a capacity review after you obtain current information. This keeps the dashboard useful for the next operator and reduces the risk of sending residents to a full or unsuitable location.

## 8. How to manage vehicles, supplies, and field resources

The **Resources** screen tracks operational assets such as rescue vehicles, boats, relief supplies, communications equipment, and supporting teams. It helps the logistics desk understand what is ready, deployed, unavailable, or waiting for replenishment.

When you record a resupply or resource update, the system marks the action and makes it visible to the next user. A resource shown as available still needs sensible real-world checks: fuel, crew, access route, weather, equipment condition, and communication contact.

## 9. How to use Response Groups

The **Response Groups** screen lists emergency teams, their specialty, most recent location, readiness, communication channel, and current assignment. It is particularly useful when several incidents happen at once and the command team must avoid assigning the same group twice.

The system can provide a recommendation for a specific incident. It compares the incident’s severity with a group’s skills, travel distance, readiness, location freshness, and known constraints. The recommendation explains why a group appears higher or lower in the list. The duty officer must still check the explanation, confirm the team by radio or another channel, and authorize the final assignment.

## 10. How to use Communications

The **Communications** screen is the shared log for dispatch messages, field updates, acknowledgement records, and simulated audio-dispatch items. Use it to keep a clear account of what was said, when it was said, and whether the receiving group confirmed it.

If an assignment is marked undelivered, do not assume the group has acted on it. Try the team’s listed alternate channel, such as VHF radio or SMS. Then record the result. This is especially important during power outages, signal interruption, and staff handovers.

## 11. What the confirmation messages mean

The Command Center gives feedback after you use an action. This feedback helps users understand whether a record changed or whether the system only recorded that an operational step took place.

| Message type | Meaning |
|---|---|
| **Updated** | A visible status or operational record was changed, such as a center review, resource resupply, team check-in, or feed refresh. |
| **Audit recorded** | The system recorded that an action, review, or decision took place. This may not change the underlying operational data. |
| **Retry requested** | The system recorded a request to try a failed notification again. Confirm receipt through another channel if the situation is urgent. |
| **Cached snapshot** | You are seeing the last saved operational picture or public weather result. Verify time-sensitive details before acting. |

## 12. A simple emergency workflow

When an incident begins, use the following practical routine. Start on **Overview** and check the Command Readiness Board. Open **Verified Alerts** to confirm the official situation. Check **Live SOS** for people requiring immediate help. Use the **Risk Map** to review hazards and safer routes. Confirm evacuation capacity before moving residents. Check **Response Groups** and **Resources** before assigning a team. Finally, use **Communications** to record the dispatch and obtain acknowledgement.

During a shift change, the outgoing operator should review the readiness board, unresolved SOS requests, active tasks, constrained centers, stale groups, and undelivered assignments with the incoming operator. Use **Quick keys → Copy handoff** as a starting briefing, then add any verbal field updates that are not in the system. The goal is to prevent an important message or decision from being lost during a busy period.

## 13. Common terms

| Term | Plain-language meaning |
|---|---|
| **SOS** | A request for emergency help from a resident or field source. |
| **Triage** | Quickly deciding how urgent a request is and what should happen next. |
| **Dispatch** | Officially assigning a team, vehicle, or resource to an incident. |
| **Verified** | Checked against a trusted or authorized source. |
| **Cached** | Saved information from an earlier time, used when a live connection is not available. |
| **Readiness** | Whether a team, center, or resource is prepared to be used safely. |
| **Constraint** | A condition that limits an action, such as a blocked road, full center, missing fuel, or unavailable crew. |
| **Audit record** | A time-stamped log showing that an action, review, or decision occurred. |

## 14. Good practice during an emergency

Use the system often, but do not let it slow down lifesaving work. Keep public messages based on verified information. Reconfirm location and availability before sending a team. Treat stale data as a warning, not as proof that a team is unavailable. Record major decisions and handovers so the next operator can continue safely.

If the Command Center shows an error or only a cached snapshot, continue using established backup procedures: VHF radio, SMS, telephone, in-person reports, barangay coordination, and written logs. When the connection returns, update the system so the shared operational picture reflects what happened.
